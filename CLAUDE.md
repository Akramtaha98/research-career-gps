## Conventions established in this codebase (follow these, don't reinvent)

- **Dual store interface**: `backend/services/store.js` exports either `memoryStore` (in-memory, `DEMO_MODE=true`) or `pgStore` (real Postgres), selected by `isDemoMode` from `config/db.js`. Every new feature needs a mirrored implementation in both — the controllers never know which one they're talking to.
- **Idempotent numbered migrations**: `backend/migrations/00N_description.sql`, always `IF NOT EXISTS`, given as copy-paste SQL. `backend/schema.sql` represents current desired state (for a fresh DB); migrations are the incremental diffs for an existing one. Keep both in sync when adding a table/column.
- **ORCID-owner-override verification pattern**, used identically in three places now (shared_scores, verified_authors, and the private scopus/wos score's "Claim my profile"): `const submitter = await store.findUserById(req.user.id); const isOwner = Boolean(submitter?.orcid) && submitter.orcid === target.orcid;`. `isOwner` submissions become instantly "verified"; everyone else's are stored as unverified suggestions that never silently overwrite an already-verified value. Reuse this exact pattern for any future "who's allowed to assert this is true" feature rather than inventing a new one.
- **Source-priority-with-fallback pattern**: try source A, catch/empty-result triggers a fallback to source B, never let both failing crash the request — see `researcherSource.js` (Semantic Scholar primary, OpenAlex fallback) and `verificationService.js`.
- **No scraping of paywalled/bot-protected sources** (Scopus, Web of Science) beyond a single best-effort, no-CAPTCHA-bypass GET with honest failure reporting — see `backend/services/externalProfileCheck.js`. This was an explicit, deliberated decision (the user first said no scraping at all, math+ORCID-check only; later asked for a "checking agent" and was given the tradeoffs again before this was built). Don't expand this into more aggressive scraping, headless-browser automation, or CAPTCHA-solving without raising it with the user first — same reasoning as before still applies (ToS risk, unreliable from a cloud IP, WOS has no public page at all).
- **i18n key parity across all 6 locales is a hard requirement**: `frontend/src/locales/{en,es,fr,de,ar,ms}/translation.json`, currently **301 keys each**. After any translation-file edit, flatten-and-diff all 6 (a short Node script does this — see git history for the exact snippet) before considering the change done. Backend-generated error/note strings (e.g. `err.response.data.error`, `externalProfileCheck.js`'s `note` field) are English-only by existing precedent and are not expected to be translated.
- **Dark mode via global class overrides, not per-component `dark:` classes**: `tailwind.config.js` has `darkMode: 'class'`; `ThemeContext` toggles a `dark` class on `<html>` and persists the choice in `localStorage` (device-level, not synced to the account). `frontend/src/index.css` retargets the app's existing slate/brand/amber/emerald/red utility classes globally under `.dark` ancestor selectors, since every page already draws from that same small palette — this covers ~15 components without touching them individually. New components should still use explicit `dark:` classes if they introduce colors outside that existing palette. Two color values in that CSS use plain hex instead of `@apply` (`text-slate-500`/`text-slate-400`) because they retarget each other, which Tailwind's `@apply` flags as circular.
- **Sandbox bash gotcha**: backticks inside a double-quoted `git commit -m "..."` string get interpreted as command substitution and silently corrupt the message. Always write the commit message to a plain file and use `git commit -F <file>` (or `--amend -F <file>` to fix one already made).
- **Sandbox `node_modules`/rollup gotcha**: this environment sometimes needs `rm -rf node_modules package-lock.json && npm install` in `frontend/` before `npm run build` works (missing `@rollup/rollup-linux-*` optional dependency, an npm bug, not a real code issue) — if you do this, `git checkout -- frontend/package-lock.json` afterward so the reinstall's incidental lockfile churn doesn't get committed.

## Feature map — everything added in this session, in order

1. **Standalone academic-verification system** (`/verify` page, separate from the Dashboard's tracked-researcher model): given an ORCID + optional self-reported claims, resolves the real profile (Semantic Scholar primary, OpenAlex fallback), compares field-by-field, persists an append-only history. Tables: `verified_authors`, `verified_author_metrics`, `verified_papers`, `verified_comparison_results`. Service: `backend/services/verificationService.js`. `journal_impact_factor` is always flagged unverifiable (neither source has it) rather than silently dropped.
2. **Import (Scopus/WOS CSV) tab removed entirely** — frontend page/route/nav/context function, backend endpoint/controller, i18n namespace, all deleted. `papers.origin` column stays for schema stability even though nothing writes `'import'` rows anymore.
3. **ORCID-owner override** added to the Verify feature (mirrors the pre-existing `shared_scores` pattern) — `verified_authors.owner_*` columns let the actual ORCID owner's self-submitted numbers act as an authoritative correction over the raw external snapshot, with COALESCE-style partial-field merging so a partial submission never wipes a previously confirmed field.
4. **Main Search/Dashboard pipeline flipped** from OpenAlex-primary to **Semantic-Scholar-primary, OpenAlex-fallback** (`researcherSource.js`), matching the Verify feature's priority. `fetchAuthorProfile` now has a symmetric cross-source paper-merge enrichment in both directions (previously only worked one way).
5. **H-index ≤ paper-count math validation**, enforced on both the private score box and the community submission, frontend and backend (`validateHIndexAgainstPaperCount` in `researcherController.js`).
6. **"Claim my profile" flow**: clicking it in the private Official H-index box opens a modal (`frontend/src/components/Modal.jsx`) offering "Open profile" (new tab) and, only if the signed-in account's ORCID matches the researcher's, "Confirm & verify" (submits to the community pool via the existing owner-override check). No ORCID match → sign-in hint instead of a disabled button.
7. **Dark/light mode toggle** — see conventions above.
8. **Footer**: "Built with ❤️", "© {{year}} Research GPS" (year computed client-side, never stale), a "Contact us" link. The "— MVP" suffix was deliberately removed.
9. **Contact Us page** (`/contact`, no login required) → `POST /api/contact` (its own tighter rate limit, 10 req/15min) → `contact_messages` table. No outbound email is wired up (no SMTP/Resend/SendGrid configured) — messages are meant to be read directly via the Supabase SQL editor, same workflow as every other admin-facing table here.
10. **Best-effort Scopus auto-check** (`backend/services/externalProfileCheck.js`) — see conventions above for the reasoning and limits. Returned as `autoCheck` alongside the save/submit response on both the private score endpoint and the community submit endpoint; rendered via `ScoreBox.jsx`'s shared `AutoCheckNote` component.
